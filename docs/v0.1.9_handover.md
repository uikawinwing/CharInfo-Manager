## 2. Architecture invariants that must not drift

CharInfo Viewer still has exactly three presentation routes:

1. Normal character
2. Special NPC
3. Trusted DX

Routing priority is fixed:

```text
Trusted DX > Special NPC > Normal character
```

Rules:

- Trusted DX identity only comes from the controlled DX placeholder + loader path.
- Name matching, metadata, normal profiles, images, or handmade fields must never grant DX identity.
- Special NPC is granted by valid visual data for the exact character name.
- `char_info.profiles[姓名]` is the official visual-profile source.
- `char_info_visuals[姓名]` is legacy compatibility only and is planned for retirement after the migration path is stable.
- Direct image syntax inside `<char_info>`, ordinary image variables, or unrelated metadata must not grant Special NPC.
- Do not introduce a fourth Viewer route.

Viewer / Creator responsibilities remain separated even though the release is a single installable bundle:

- Viewer Runtime owns player browsing, current-character library, worldbook character library, refresh, read-only display, and explicit player Save actions.
- Creator Manager owns visual-profile authoring, migration/import UX, managed EJS generation, and explicit author saves.
- Viewer must not silently migrate or rewrite legacy data during ordinary viewing.
- Creator is mounted only when opened and destroyed when closed.

## 3. What the stabilization line delivered

### 3.1 Viewer / Creator reunification

- Viewer and Creator ship as one script again.
- Internal `viewer`, `creator`, `shared`, and `runtime` responsibilities remain separate.
- the old cross-script host bridge was removed.
- Viewer talks to Creator through a narrow same-bundle controller.
- Creator Preview uses the real Viewer in read-only draft mode.

### 3.2 Routing and data safety

- DX trust gating is isolated from ordinary character/profile data.
- production build physically excludes private DX implementation data through the stable production adapter path.
- Special NPC routing only accepts the controlled visual-profile sources.
- ordinary Viewer flow remains read-only unless the player explicitly invokes Save.
- Viewer no longer automatically writes legacy gallery migrations back into character data.

### 3.3 Save, refresh, and media fallback

- Special NPC Save supports explicit MVU/chat-state write and current chat worldbook write.
- worldbook Save writes clean YAML rather than a `<char_info>` wrapper.
- save feedback follows the actual operation/read-back result instead of a detached host popup.
- current-character refresh rereads the latest MVU/chat variables and remounts controlled CharInfo floors.
- Creator "apply saved version" reuses the same controlled refresh path.
- Viewer and Creator Preview use ordered `sources[]` fallback on error, timeout, retry, and exhaustion.
- Catbox/static media keeps the author's original URL instead of being unnecessarily rewritten through wsrv.

### 3.4 Special NPC UI work

Desktop and mobile Special NPC presentation was heavily stabilized without changing Normal Viewer routing.

Highlights:

- desktop overview/panel hierarchy was rebuilt;
- mobile overview is portrait-first;
- mobile detail pages reuse the currently selected portrait as translucent wallpaper;
- animated/video wallpaper freezes the current frame when needed;
- skills are grouped by active/passive/other while preserving author order within each group;
- holdings are grouped into equipment/item sections;
- group panels are framed, independently collapsible, and default expanded;
- skill type is represented by shape while rarity remains color;
- internal scrollbars are visually hidden where appropriate while scrolling remains available;
- redundant page-title duplication was removed from Special NPC detail tabs.

### 3.5 v0.1.9 mobile manager fixes

The final mobile stabilization pass fixed several independent problems.

Worldbook character library:

- fixed the overlay positioning inside the existing library host;
- aligned the mobile breakpoint to `720px`;
- removed the desktop three-column header grid from mobile intrinsic sizing;
- constrained long worldbook names/select controls so they cannot widen the page;
- added the missing mobile `更多 -> 视觉编辑` Creator entry;
- kept mobile detail dialogs within the available width.

Creator Preview:

- desktop still uses fit-to-stage scaling;
- mobile no longer scales the entire long Viewer down to a postage stamp;
- mobile Preview uses real mobile width with `scale = 1` and vertical scrolling;

Current Character Viewer:

- fixed the real Chrome DevTools geometry bug where Current Character forced `height: 100%` while Special NPC still kept `aspect-ratio: 2 / 3`;
- in the embedded Current Character mobile Viewer only, Special NPC now uses `aspect-ratio: auto`, so the shell obeys the available width instead of expanding media beyond the viewport;
- the ordinary chat Special NPC Viewer keeps its normal `2:3` mobile card behavior.

## 4. Important debugging lessons from v0.1.9

### 4.1 Chrome Device Mode outer canvas is not the mobile viewport

In Chrome DevTools Device Mode, the purple/empty area outside the emulated phone rectangle is desktop DevTools canvas, not unused SillyTavern viewport.

Do not try to make CharInfo expand into that outer canvas.

When investigating mobile sizing, inspect actual element geometry (`getBoundingClientRect`, DevTools tooltip/computed dimensions) inside the emulated viewport.

### 4.2 The final Current Character bug was a geometry conflict, not a JS error

Chrome DevTools showed:

```text
video.illustrated-portrait-video.is-loaded ≈ 475.33 × 655
```

while the emulated viewport was only about 414px wide.

There was no relevant CharInfo Vue/runtime exception and no video decode failure. The width came from:

```text
Current Character: height: 100% !important
+
Special NPC mobile: aspect-ratio: 2 / 3
=
height-driven width larger than the viewport
```

The fix belongs at the embedded shell geometry layer, not in media loading.

### 4.3 Do not promote runtime hosts across frames without hard evidence

A temporary attempt to solve the mobile sizing issue by walking from `window.parent` toward a higher/top frame did not change the real bug and was reverted.

Current runtime host boundaries should not be changed merely because Device Mode shows outer desktop canvas around the phone viewport.

## 6. Legacy `char_info_visuals` status

The Viewer still temporarily recognizes legacy exact-name data under:

```text
char_info_visuals[姓名]
```

Known legacy fields used by the current compatibility path include:

```text
url
gallery: string[]
custom_racecolor
custom_tiercolor
登场台词
```

Current Creator behavior is intentionally conservative but unfriendly:

- it detects unmanaged `char_info_visuals` EJS;
- marks the entry blocked;
- refuses automatic Save;
- tells the author to back up/remove the old visual code manually.

This is the main migration friction to solve in v0.2.0.

The long-term direction is not to maintain two runtime profile systems forever. Creator should become the migration bridge, then Viewer compatibility can be retired later.

## 7. Existing story behavior

`<char_info>` already supports the ordinary field:

```yaml
背景故事: |
  ...
```

Viewer already parses and displays that text.

For v0.2.0, the two story sources have different responsibilities:

- `<char_info>.背景故事` remains the concise LLM-facing summary used by normal CharInfo data flow, variable injection, and worldbook/context usage;
- `metadata.story_sections` becomes the human-facing author-written display story.

Do not rewrite or migrate the user's original `<char_info>.背景故事` merely to support the new Creator story feature.

Creator should not expose the generated `<char_info>.背景故事` as an authoring field or read-only maintenance field. The creator only authors the human-facing display story; the generated summary remains an internal runtime/context source.

Viewer display resolution should be:

```text
metadata.story_sections has content
  -> display only the author-written metadata story
  -> hide <char_info>.背景故事 from the human-facing story view

no metadata.story_sections
  -> fall back to the existing <char_info>.背景故事 display
```

This is a display override only. It must not replace, expand, or write the author story back into the compact `<char_info>` data used for LLM context.
