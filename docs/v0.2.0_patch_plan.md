# CharInfo Manager v0.2.0 Patch Plan

> Proposed next feature release after `v0.1.9`.
>
> Main themes: metadata, author-defined story sections, Viewer story presentation, and a safe Creator migration bridge from legacy `char_info_visuals[姓名]`.
>
> This plan supersedes the old `v0.1.8+` checkpoint numbering in the historical roadmap.

## 1. Product goal

v0.2.0 should make the current visual-profile system useful for more than images/colors while also lowering the migration cost for creators who still use the old `char_info_visuals[姓名]` structure.

The release has four primary goals:

1. extend the managed profile with optional character metadata;
2. let creators author ordered human-facing story sections without rewriting the original concise `<char_info>` story used for LLM context;
3. use those author-written sections as a Viewer-only display override without creating a new Viewer route or overcrowding mobile navigation;
4. detect supported legacy `char_info_visuals[姓名]` EJS, statically import it into the Creator draft, and let the author upgrade to the new managed profile instead of manually copying/removing old fields.

Long-term direction:

> Runtime compatibility with `char_info_visuals` is temporary. Creator should remain capable of importing old data even after Viewer no longer renders the legacy structure.

## 2. Non-goals

v0.2.0 must not:

- create a fourth Viewer type;
- allow metadata to grant DX or Special NPC identity;
- rewrite the original `<char_info>` YAML during ordinary visual editing;
- silently execute arbitrary legacy EJS to discover values;
- automatically delete unrecognized legacy code;
- redesign Normal Viewer;
- redesign trusted DX presentations;
- make Viewer perform background migrations;
- merge Creator and Viewer responsibilities;
- add Gallery Lightbox unless the core v0.2.0 checkpoints are already complete and separately approved.

## 3. Proposed profile schema v2

Current managed runtime profile uses `schema_version: 1`.

Adding metadata should promote the official profile contract to `schema_version: 2`.

### 3.1 TypeScript model

Proposed shared types:

```ts
export interface CharacterStorySection {
  title: string;
  content: string;
}

export interface CharacterProfileMetadata {
  author?: string;
  version?: string;
  author_note?: string;
  sex?: string;
  race?: string;
  story_sections?: CharacterStorySection[];
}

export interface CharacterVisualProfile {
  characterName: string;
  avatarUrl: string;
  raceColor: string;
  tierColor: string;
  entranceQuote: string;
  gallery: GalleryImage[];
  galleryExtension?: GalleryExtensionReference;
  metadata?: CharacterProfileMetadata;
}
```

Persisted runtime profile:

```js
char_info.profiles[姓名] = {
  schema_version: 2,
  custom_racecolor: '...',
  custom_tiercolor: '...',
  '登场台词': '...',
  gallery: [...],
  gallery_extension: { ... },
  metadata: {
    author: '...',
    version: 'v0.0.3',
    author_note: '...',
    sex: '...',
    race: '...',
    story_sections: [
      { title: '...', content: '...' },
      { title: '...', content: '...' },
    ],
  },
};
```

Only non-empty optional values should be emitted.

If all metadata fields are empty, omit `metadata` entirely.

If there are no story sections, omit `story_sections` rather than saving an empty array unless implementation simplicity strongly requires otherwise.

### 3.2 Backward compatibility

Managed profile v1 must continue to load.

Opening a v1 managed profile and saving it through v0.2.0 should produce a valid v2 managed profile while preserving all existing visual data.

No metadata is required for a valid profile.

### 3.3 Validation rules

Metadata is presentation/authoring information, not routing identity.

Rules:

- metadata must never grant DX;
- metadata alone must never grant Special NPC;
- metadata cannot override the exact character name used by the profile path;
- story section order is author order and must remain stable;
- temporary editor IDs must never be serialized;
- `title` and `content` must be EJS-safe and must not contain `<%` or `%>`;
- empty sections should be removed during normalization rather than persisted as meaningless objects;
- metadata normalize/validate must be isolated in shared code, not duplicated in Creator and Viewer.

Avoid small creative-writing length limits. If a technical safety cap is needed, make it large and document it as a transport/safety bound rather than a writing recommendation.

## 4. Metadata semantics

The existing `<char_info>` data remains the primary character/context data source for the LLM-facing workflow.

`metadata` is authoring/presentation information. In particular, `metadata.story_sections` is allowed to override the story shown to the human reader without replacing the concise `<char_info>.背景故事` used by variable/worldbook/context injection.

### 4.1 `author`

Purpose:

- optional attribution for the visual/story profile;
- can be shown subtly in story reading, worldbook cards, and worldbook detail UI;
- worldbook-library search/sort may use the author value, while the default library order must remain the original worldbook order;
- must not affect routing or data import.

### 4.2 `sex`

Purpose:

- optional creator-supplied library/profile metadata;
- initially expose through the ViewModel/Creator and use only as a presentation fallback where appropriate;
- do not overwrite `<char_info>` fields or MVU data.

### 4.3 `race`

Purpose:

- optional creator-supplied metadata for human-facing worldbook/library presentation, filtering, and race grouping/sorting;
- when present, `metadata.race` is the preferred worldbook-library display/filter/sort value; current chat data, static character data, and entry-title parsing are fallbacks in that order;
- this presentation priority does not rewrite or replace `<char_info>.种族` in character/context data;
- must not determine theme, Special NPC routing, or DX identity by itself.

### 4.4 `story_sections`

Purpose:

- author-managed, human-facing story chapters/sections;
- independent from the original `<char_info>.背景故事` field;
- when non-empty, acts as the Viewer display replacement for `<char_info>.背景故事` rather than an appendix to it;
- `<char_info>.背景故事` remains the concise LLM-facing summary used by the character/context data flow;
- preserves author order;
- Creator edits this metadata only and does not rewrite the original character YAML.

## 5. Creator metadata and story editor

Main UI location: Creator Step 2 / character information area.

### 5.1 Metadata fields

Add optional controls for:

- 作者
- 性别
- 种族

These should remain visually secondary to the core visual configuration.

### 5.2 Story section editor

Add an ordered editor for custom story sections.

Required actions:

- add section;
- edit title;
- edit content;
- move up;
- move down;
- delete;
- preserve order after save/reload.

Each editor section may have an internal UI-only ID for stable Vue keys, but serialization must output only:

```text
title
content
```

Do not persist temporary IDs.

### 5.3 Existing `<char_info>.背景故事`

Creator visual editing must not rewrite the user's original `<char_info>.背景故事`.

Creator should **not expose that generated background-story field as an editable or read-only authoring control**. It is runtime character data produced by the normal CharInfo/LLM flow, not something the visual-profile creator is responsible for maintaining.

The Creator story UI should therefore contain only the human-authored Viewer story editor, for example:

```text
Viewer 展示故事
```

The internal distinction between the generated `<char_info>.背景故事` and the author-written display story belongs to the data/runtime layer, not to the Creator form UX.

The real Viewer Preview must still follow the final display precedence automatically:

```text
draft metadata.story_sections exists
  -> Preview shows only the author-written display story

no draft metadata.story_sections
  -> Viewer Preview may fall back to the runtime <char_info>.背景故事 when that data is available
```

This fallback is a Viewer behavior, not a Creator field. The author does not need to inspect, synchronize, or approve the generated summary from the Creator UI.

Saving metadata must not copy the long author-written story back into `<char_info>`, MVU character data, or worldbook injection data.

### 5.4 Real Viewer Preview

The existing real Viewer Preview must immediately reflect draft metadata/story changes.

Preview continues to be:

- read-only with respect to chat/worldbook state;
- isolated from DX auto-injection;
- based on the unsaved Creator draft;
- destroyed when Preview closes.

## 6. Viewer story presentation

The current Special NPC mobile navigation is already dense:

```text
首页 / 面板 / 档案 / 技能 / 持有 / 登神
```

v0.2.0 should **not** add a permanent seventh global mobile tab just for stories.

### 6.1 Special NPC design

Keep the existing six main navigation items.

Inside `档案`, add a secondary view only when custom story sections exist:

```text
[ 资料 ] [ 故事 ]
```

Rules:

- default remains `资料`;
- if `metadata.story_sections` is empty, do not show the secondary switch at all;
- the six-item desktop/mobile main navigation remains unchanged;
- this is still the same Special NPC route, not a new presentation type.

### 6.2 Story display precedence

When the Story subview is available:

1. `metadata.story_sections` is the human-facing display source;
2. show those sections in exact author order;
3. do **not** additionally show `<char_info>.背景故事` in the same human-facing story view;
4. optionally show `metadata.author` as quiet attribution;
5. never merge or write the display story back into the underlying `<char_info>` data.

The resolution rule is:

```text
if metadata.story_sections has at least one valid section:
    displayedStory = metadata.story_sections
else:
    displayedStory = <char_info>.背景故事
```

The fallback exists so characters without author-written display metadata keep their current readable story.

If no custom sections exist, current Viewer behavior remains unchanged.

The concise `<char_info>.背景故事` must remain available to the existing character data / variable / worldbook context flow even while it is hidden from Viewer display by custom story metadata.

### 6.3 Story visual treatment

Desktop:

- use the existing Special NPC detail content pane;
- readable text width, generous line-height, no giant title duplication;
- each story section uses a clear chapter heading and body;
- page scrolls as a whole; do not create one nested scroll area per section.

Mobile:

- reuse the existing translucent selected-portrait wallpaper treatment used by Special NPC detail pages;
- keep text on a readable content surface;
- preserve the normal bottom navigation;
- story content scrolls vertically in the page;
- do not shrink typography to force everything into one screen.

### 6.4 Normal and DX Viewer

Normal Viewer:

- do not redesign it in this release;
- existing `背景故事` behavior remains.

Trusted DX:

- existing DX storybook/presentation behavior remains independent;
- generic metadata must not replace DX-specific story presentation without a separate approved DX task.

## 7. Legacy `char_info_visuals[姓名]` migration bridge

This is a core v0.2.0 feature.

### 7.1 Current problem

Creator currently treats any unmanaged `char_info_visuals` usage as blocked:

```text
检测到旧版视觉配置
暂时无法自动保存；请先备份并移除旧版视觉配置。
```

This forces legacy creators to manually inspect/copy/delete code before they can use the new Creator.

The new behavior should make migration the easy path.

### 7.2 New inspection API

Add a dedicated static inspector in shared code, separate from normal managed-block inspection.

Example conceptual result:

```ts
type LegacyVisualInspection =
  | { state: 'absent' }
  | {
      state: 'importable';
      characterName: string;
      profile: CharacterVisualProfile;
      start: number;
      end: number;
      warnings: string[];
    }
  | { state: 'unsupported'; reason: string };
```

The inspector must not execute the entry.

### 7.3 Supported legacy shape for v0.2.0

Primary target:

```js
setLocalVar('char_info_visuals["角色名"]', {
  url: 'https://...',
  gallery: ['https://...', 'https://...'],
  custom_racecolor: '#RRGGBB',
  custom_tiercolor: '#RRGGBB',
  登场台词: '...',
});
```

Equivalent direct bracket-path quoting styles can be supported if they remain statically recognizable.

Do not attempt to support arbitrary dynamically constructed paths or objects in the first version.

### 7.4 Parsing safety

Legacy import must be static.

Allowed approach:

1. identify a direct `setLocalVar` path targeting one exact `char_info_visuals[姓名]`;
2. extract the object-literal source with balanced-brace scanning;
3. parse only a JSON/JSON5-like literal;
4. reject function calls, expressions, template execution, variables, or dynamic values;
5. require the exact selected character name when known;
6. return `unsupported` instead of guessing.

Never use:

- `eval`;
- `evalTemplate`;
- EJS execution;
- the SillyTavern generation/template runtime merely to discover legacy values.

### 7.5 Legacy field mapping

Known mapping:

```text
legacy url               -> first/new main gallery image
legacy gallery[]         -> remaining ordered gallery images
legacy custom_racecolor  -> raceColor
legacy custom_tiercolor  -> tierColor
legacy 登场台词          -> entranceQuote
```

Rules:

- accept only valid HTTPS media URLs;
- deduplicate while preserving order;
- `url` comes first when valid;
- when there is no `url`, the first valid legacy gallery item becomes `主立绘`;
- do not infer `avatarUrl` from legacy `url`; old `url` means portrait/media, not avatar;
- unknown legacy keys are not silently converted into unrelated new fields.

Legacy gallery-only profiles currently randomize the first displayed image in the old Viewer compatibility path. The new managed profile uses an ordered main image. Migration UI should warn about that behavior change rather than inventing an unrelated new randomization field in v0.2.0.

### 7.6 Creator autofill behavior

When selecting an entry:

1. if a valid managed block exists, load it normally;
2. otherwise inspect supported legacy `char_info_visuals[姓名]`;
3. if importable, automatically populate the Creator draft;
4. do not write anything yet;
5. show a visible migration banner.

Suggested message:

```text
检测到可迁移的旧版 CharInfo 视觉配置。
已自动预填到新版编辑器；当前世界书尚未修改。
保存后可升级为 char_info.profiles v2。
```

Entry state should be something like:

```text
legacy-importable
```

rather than the current generic blocked state.

If the legacy code is dynamic/ambiguous, keep the entry blocked and explain why it cannot be safely auto-imported.

### 7.7 Migration Save UX

For an importable legacy entry, primary Save copy should clearly say:

```text
升级并保存新版配置
```

Saving must:

1. validate the imported/edited draft;
2. generate the new managed v2 block targeting `char_info.profiles[姓名]`;
3. preserve unrelated entry content/EJS;
4. if the exact legacy statement range is statically and safely known, offer removal of that exact statement;
5. re-read the entry after Save and verify the new managed block.

Recommended safe-removal UI:

```text
[x] 保存成功后移除已识别的旧版 char_info_visuals 配置
```

Default checked only when the importer has an exact removable source range.

If safe removal cannot be proven:

- save may create the new managed profile only if doing so cannot corrupt the entry;
- keep the old code untouched;
- show a clear cleanup warning;
- never delete surrounding or unknown EJS.

### 7.8 New Creator output policy

After v0.2.0:

> Creator must never generate new `char_info_visuals` output.

All new/updated profiles use:

```text
char_info.profiles[姓名]
```

Legacy support is import-only.

## 8. Planned retirement of Viewer legacy compatibility

The goal is to stop maintaining two runtime visual systems.

### Phase A — v0.2.0 migration release

- Viewer still reads `char_info_visuals[姓名]` temporarily.
- Creator detects/imports supported legacy profiles.
- Creator encourages one-click upgrade.
- all official docs/examples should use the new profile system.
- legacy runtime path is marked deprecated in code comments/tests/docs.

### Phase B — migration window

Keep at least one stable release window where:

- legacy Viewer still works;
- Creator migration is proven in real worldbooks;
- unsupported legacy shapes are identified and either deliberately supported or documented as manual cases.

No telemetry is required.

Readiness is determined by tests, official content migration, and actual creator feedback.

### Phase C — proposed later cleanup release (target: v0.3.0 unless reprioritized)

Remove legacy `char_info_visuals` consumption from Viewer routing/theme resolution.

Important:

- **retain the Creator legacy importer** so an old creator can still open an old worldbook and upgrade it even after Viewer runtime compatibility is gone;
- remove legacy runtime-specific tests after replacement migration tests exist;
- old legacy-only profiles should no longer grant Special NPC after runtime compatibility removal;
- release notes must warn clearly before this removal ships.

Exit criteria before Phase C:

1. all official examples/samples use `char_info.profiles`;
2. Creator importer covers the known direct legacy structure with robust tests;
3. safe migration Save/removal has been tested in SillyTavern;
4. at least one stable migration release has shipped;
5. documentation tells legacy authors how to upgrade.

### Compatibility stabilization completed between Checkpoint 2 and 3

During Checkpoint 2 field testing, several existing Viewer/runtime compatibility bugs were exposed, especially on a Redmi K60 / Android Chrome environment and on desktop zoomed or height-constrained layouts. These are treated as stabilization work rather than new v0.2.0 feature scope.

Fixed issues and root causes:

- **Chat visual profile exists but an already-mounted card stays Normal**: Viewer could initialize before `chat` variables were restored. Later variable events refreshed the character library but did not remount active chat cards, while the message render dedupe key ignored variable changes. Runtime now performs a controlled active-floor visual refresh after variable initialization/update so cards re-read `char_info.profiles`.
- **Mobile worldbook library bottom dock missing**: the CharInfo host was already fixed to the viewport, while the inner dock used another `position: fixed`. Nested fixed positioning behaved inconsistently under Android visual viewports. The dock is now anchored to the CharInfo host with absolute positioning.
- **Mobile character tap hides the dock but detail UI does not appear**: state transition to detail succeeded, but the detail overlay itself used another nested fixed layer and could render against the wrong viewport. The detail layer is now host-relative `absolute` positioning.
- **Mobile character card hit target unreliable while the enable toggle still works**: only the avatar button and a text subregion opened details. The whole character card is now the detail hit target; the enable toggle stops propagation and remains an independent action.
- **Special NPC overview clipped at browser/system zoom or in a short floating viewer**: the overview intentionally used hidden overflow for screenshot-oriented composition, and the flex height chain lacked a complete `min-height: 0` contract. This could make the inner panel believe it was not overflowing while an outer layer clipped it. The normal/compact/dense flow remains, with a real scroll fallback when content still exceeds the available height.
- **Special NPC attributes reflow from 3+2 into 2+2+1**: fixed-width flags inside a wrapping flex container changed row count when the data pane narrowed. Special NPC now treats 3+2 as a visual contract and shrinks flag width when necessary instead of changing row count.
- **`forceMobileLayout` appeared enabled but Viewer internals stayed desktop**: the setting reached runtime/manager shells but was not propagated through `ViewerApp -> IllustratedCharacterSheet -> IllustratedTabNav`. It is now a real Viewer input and changes the internal Special NPC mobile structure.
- **Forced-mobile desktop layout became either a 414px postage stamp or an ultra-wide stretched card**: mobile structure, physical phone width, and outer floating-window sizing had been coupled. Runtime also had old `max-width: none`, `height: 100%`, and `aspect-ratio: auto` overrides that defeated component constraints. Responsibilities are now separated: Viewer owns mobile structure; Runtime owns the host window. Real phone layout keeps the 414px contract, while desktop forced-mobile uses a centered responsive canvas up to 640px with Special NPC 2:3 geometry and scrolls the viewer region when height is insufficient.

Regression direction for future mobile reports:

- prefer host-relative positioning over nested viewport-fixed layers;
- treat `height: 100%`, `min-height: 0`, and overflow ownership as one flex sizing contract;
- do not infer that a device-specific report is a device-specific API failure until viewport/layout layering is ruled out;
- forced layout settings must change component structure explicitly rather than copying only outer-shell media-query CSS.

### Runtime/data stabilization completed after Checkpoint 4

Field testing of metadata and the worldbook library exposed several cross-layer issues that are now covered by regression tests:

- **Vue reactive metadata attachment**: Viewer-only metadata is attached as a non-enumerable configurable property. A non-configurable/non-writable object-valued attachment can violate Vue Proxy invariants even when pure data/service tests pass. New presentation data must be tested through a real `reactive()` boundary, not only through pure functions.
- **Unknown-field tolerance**: unrecognized profile or `metadata.*` keys are ignored. Known fields continue to work and the profile must not lose Special NPC eligibility merely because a future/unknown key is present.
- **Variable lifecycle**: both variable initialization and completed variable updates refresh the worldbook/current-character libraries and remount active CharInfo cards so they read the latest profile data.
- **Worldbook presentation precedence**: managed metadata is the preferred human-facing source where explicitly supported. In particular, library race uses `metadata.race -> current chat race -> static worldbook race -> entry-title heuristic`; author/version/author note prefer metadata and only use legacy title parsing as fallback where applicable. This does not rewrite `<char_info>` facts or affect Viewer routing.
- **Worldbook discovery UX**: library search indexes race/author/version/author note; race filtering uses the resolved presentation race; stable sorting supports original worldbook order, name, race, author, encountered-first, and enabled-first. Original worldbook order remains the default. Cards may show a compact author signature but do not display sex metadata.

Pre-push automated gate on 2026-08-16 after these changes:

- `304 / 304` tests passed;
- ESLint passed with zero errors;
- production webpack build passed;
- generated runtime bundle is approximately `1.11 MiB` and only the existing webpack size warnings remain.

## 11. UX language direction

Migration copy should be encouraging rather than punitive.

Avoid making legacy creators feel their content is invalid.

Prefer:

```text
检测到旧版 CharInfo 视觉配置，已为你预填到新版编辑器。
保存即可升级；保存前不会修改世界书。
```

Avoid default wording like:

```text
旧版配置不支持，请手动删除。
```

For unsupported dynamic legacy code, be precise:

```text
检测到旧版视觉代码，但其中包含动态表达式，无法安全自动读取。
```

## 12. Definition of done for v0.2.0

v0.2.0 is not complete until all of the following are true:

- metadata v2 contract is stable;
- old managed v1 profiles still load and can upgrade safely;
- Creator can edit ordered story sections;
- Viewer presents custom stories as a display-only replacement for the concise `<char_info>` background story without changing the three-route architecture;
- the long human-facing story is never written back into the LLM-facing `<char_info>.背景故事` automatically;
- mobile Special NPC navigation remains clean;
- supported `char_info_visuals[姓名]` profiles auto-fill in Creator;
- migration Save writes only the new profile system;
- safe old-code removal is exact and non-destructive;
- Viewer ordinary browsing remains read-only;
- metadata cannot grant DX/Special identity;
- full tests, lint, production build, and live SillyTavern QA pass;
- release notes clearly state that `char_info_visuals` runtime compatibility is deprecated and will be removed after the migration window.

## 13. Future plan — imgbed-backed library thumbnails

This is intentionally **not** part of the current v0.2.0 implementation pass.

The Creator must continue to ask authors for only one normal image upload/URL. Authors should not need to understand or manually upload a separate thumbnail asset.

Once the project imgbed can return a stable thumbnail for an uploaded image, the Worldbook Character Library should use that capability automatically:

- upload/storage layer may return both the original image URL and an optional derived thumbnail URL;
- if a thumbnail already exists, reuse it instead of generating/uploading another one;
- library cards request the thumbnail while character detail and full Viewer keep the original media URL;
- keep `loading="lazy"` so opening a large worldbook does not immediately download every cover;
- do not require a new Creator-facing thumbnail field;
- do not generate client-side thumbnails by first downloading the full original image, because that does not save first-load bandwidth;
- animated media/video handling stays separate from static cover-thumbnail generation.

Until imgbed support is ready, keep the current cover behavior rather than adding a second ad-hoc thumbnail cache/proxy contract inside CharInfo.
